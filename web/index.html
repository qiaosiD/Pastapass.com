How this works — in plain English

No jargon. The whole project, start to finish, the way you'd explain it to a friend.

1

The question

Some things sell out the second they go on sale — concert tickets, sneaker drops, limited-edition passes. Gone in seconds. So here's the question this project pokes at: can a small program click “Buy” faster and more reliably than a person mashing the button? And if so — how, and by how much?

2

The honest catch (this part matters)

You'll hear people brag their bot “clicks within one millisecond.” That's not really a thing. When a sale opens, the “it's live now” signal has to physically travel across the internet to your computer — and that trip takes tens of milliseconds, every time, no matter how clever the code is. Nothing beats the speed of light down a wire.

So the real contest isn't raw clicking speed. It's being ready — already signed in, already connected, already aimed — and reacting the instant the button lights up, a hair faster than everyone else.

3

Three ways to grab it

The project races three strategies head-to-head:

  • A real web browser that loads the page like a human would and clicks the button the moment it appears. Most realistic — but a whole browser is slow to react.
  • Skipping the browser entirely and talking straight to the store's server — just the bare request, nothing else. Fastest by far, but fragile and fiddly to set up.
  • A hybrid — keep a real browser for the “stay logged in / look human” part, but fire the actual purchase request directly. The practical middle ground.
4

Measuring it without cheating

Here's the tricky bit. To compare strategies you have to time them. But if you clock the click on your computer and the sale opening on their computer, the two clocks won't agree — and they disagree by exactly the few milliseconds we're trying to measure.

The fix: let one computer be the only stopwatch. A stand-in “store” marks the exact instant it makes the button live and the exact instant the click lands, then subtracts. One clock, no disagreement, no fudging the numbers.

5

What we actually found

  • Skipping the browser is ~4–5× faster than clicking a rendered button — a whole browser in the path really costs you.
  • Warming up the connection ahead of time (opening it before the drop, not at the last second) shaves off about a quarter of the delay.
  • Firing on a precise, pre-set schedule — instead of waiting to notice the sale opened — beats reacting by roughly 20%.
  • The programming language barely matters. Rust edges Python, but they're all within a whisker. The strategy is what wins, not the language.
6

The honest fine print

  • Nothing here touches a real store. Everything runs against a fake copy built for testing — no real product, no real payment.
  • These gaps get bigger on real internet. The tests run on one computer talking to itself, where distances are tiny; over a real home connection the differences grow a lot.
  • Real drops fight back. Big sales often funnel everyone into a random “waiting room” lottery — and when it's a lottery, being fast doesn't help. This is a study of the mechanics, not a how-to for jumping a real queue.

Three ways to be first

Speed goes up, robustness goes down, complexity goes up — pick your poison.

A

Real browser + MutationObserver

A genuine Chromium (Playwright) loads the page like a human — real cookies, real JS, real session. It watches the DOM and clicks the BUY button the microsecond it appears.

  • Slowest — a whole browser sits in the path
  • Most realistic — indistinguishable from a person
  • Runs anywhere: a laptop or a cheap VPS
B

HTTP-direct + pre-warmed socket

No browser at all. It parks a long-poll on the “is it live?” endpoint and holds a warm keep-alive socket, then fires the raw /buy request the instant the signal lands.

  • Fastest by far — just bytes on a wire
  • Brittle — you must reverse-engineer the exact request
  • Best on a VPS in the target’s region
C

Hybrid — warm browser, injected fetch

Keeps a real, logged-in browser for the session and anti-bot cover, but skips the rendered click — it fires the underlying request straight from in-page JavaScript.

  • Near-B speed with A’s legitimacy
  • The pragmatic sweet spot
  • Needs a real session to shine

Why the number is trustworthy

The hard part of a benchmark like this isn’t the bots — it’s the clock.

Comparing a timestamp taken on the bot’s machine to one taken on the server is meaningless at microsecond scale — the two clocks aren’t synchronized. So the mock server is the single clock of record:

  • it stamps t_release the instant it makes the button live,
  • it stamps t_hit the instant the /buy request lands,
  • and reports t_hit − t_release — both from the same monotonic counter.

The release moment is jittered and never revealed to the bot, so a strategy has to genuinely react to the signal rather than predict the clock. One process, one counter, zero cross-machine sync error. 

// inside the mock server — one monotonic clock
const tHit = process.hrtime.bigint();  // stamp FIRST
if (state !== RELEASED) return tooEarly();
const latency = tHit - tRelease;    // nanoseconds
// every approach races the same endpoint,
// so this number is directly comparable.

Syncing to the drop's clock

The single highest-leverage lever — fire at the wrong instant and nothing else matters.

Your computer's clock and the store's server clock don't agree — and they can disagree by exactly the few milliseconds you're trying to win. Fire on your wall clock and you're either early (rejected) or late (missed).

So a proactive bot fires on their clock instead:

  • Sample a live time endpoint (/api/server-time) a few times.
  • Compute the offset the way NTP does — correct for the round-trip by taking its midpoint.
  • Schedule the fire against the server's launch instant, offset-corrected — keeping a reactive long-poll as a backstop.

The gotcha: you can't read the time off a page's cached Date header — a CDN freezes it (in testing we caught one reading 15+ hours stale). Sync off a live endpoint, never a cached response. This is what lets proactive beat reactive (#004), and why clock accuracy tops the levers. 

// offset = your clock − the server's, midpoint-corrected
const t0 = now();
const { now: server } = await get("/api/server-time");
const t1 = now();
const offset = server - (t0 + t1) / 2;

// fire AT the launch instant, on the server's clock
fireAt(launch - offset);
// bots/python/clock_sync.py does this, plus a live countdown
